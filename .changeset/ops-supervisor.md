`@tangleai/ops/supervisor` runs the operations runtime in a `worker_threads` worker with its own store. `superviseOps` starts the worker and reads it through the `job_queue` contract over a MessageChannel, so the person's cancel reaches the thread where the leases live. The worker entry calls `runOpsWorker`. A worker that exits or throws is restarted after a backoff of 1 s doubling to 60 s. One that does not answer its health call is restarted as hung, and one whose heartbeat is old is restarted only after two consecutive old readings, so a clock jump or a slow start is not taken for a death. While it starts the queue answers `OS0195`, which is now a declared answer of the contract. `stop()` drains the history first. Measured over ten deaths of the worker: each was running again within 0.3–1.3 s with no claim error, no single-send operation was called twice, and every lost single-send job is recorded as `not-repeated`. Start-up reconciles only the last `keepDays`, about 250 ms over 86,000 events. The browser runtime polls once a second instead of four times. The Tangle desktop app, started with `--ops <host module>` or `TANGLE_OPS_MODULE`, runs the module's registry in such a worker, with its own `ops.db` beside the desktop's database. Its `/api/job-queue` serves the runtime under scope `ops` and the desktop store's own queue under scope `desktop`.
